# MOD0015 — This program's own registrations can move into a module

**Severity:** Info · **Category:** FusionModules.Usage · **Code fix:** yes

Not a defect. It marks the first step of moving a microservice into a modular monolith: the
service's `Program.cs` (or `Startup.cs`) becomes a module **in the same project**. The project stays
an executable and runs exactly as before — ASP.NET Core runs the entry assembly's own
`[assembly: HostingStartup]` without it being named in `HOSTINGSTARTUPASSEMBLIES` — but what the
service registers and maps of its own now sits in a `Module` class, ready for the day the project
becomes a library and a monolith's host loads it beside the others.

The diagnostic exists to carry that conversion as a code fix, so that it runs where refactorings do
not: `dotnet format`, a script, an agent. In an IDE the same conversion is also a refactoring on
`Program.cs` or `Startup.cs`, offered wherever the caret is in the top-level statements, `Main`,
`ConfigureServices` or `Configure`.

## Run it

```bash
dotnet format analyzers src/Ordering.API/Ordering.API.csproj --diagnostics MOD0015 --severity info
```

Without `--severity info` it skips the rule: a suggestion is below the default `warn`.

From Git Bash on Windows, pass the path in Windows form (`"$(cygpath -w "$PWD")\\src\\Ordering.API\\Ordering.API.csproj"`);
given `/c/...`, `dotnet format` matches no document and changes nothing, without an error.

Give it the **solution** instead of the project to have the service's own project references count
as its own code (see below): with only the project loaded there is no other program to compare with.

```bash
dotnet format analyzers eShop.slnx --diagnostics MOD0015 --severity info --include src/Ordering.API/
```

`dotnet format` writes `<Compile Include="Module.cs" />` into the project file — its workspace does
that for every document a fix adds — while the SDK includes `Module.cs` by default already. The
package's build targets drop the duplicate, whatever name the fix gave the file (`Module2.cs`,
`OrderingApiModule.cs`; see [msbuild.md](../msbuild.md#fusionmodulesdeduplicatemodulefile)), so the
build does not fail with NETSDK1022; the line is redundant and can be deleted. (A project that
consumes the analyzers without the package's targets has to delete it.)

## What moves

Into `Module.cs`, next to the project file: `internal sealed class Module : ModuleBase` in the
project's root namespace — the same name every module in the samples has (another name only if the
namespace already has a type called `Module`) — with `[assembly: HostingStartup(typeof(…Module))]`
and only the usings the global ones do not cover.

- **Registrations** that start from the builder (`builder.AddXxx()`, an extension of
  `IHostApplicationBuilder`), from `builder.Services`, or from a `Startup`'s `IServiceCollection`, and
  whose first call — and every later call of the chain on the builder or the service collection — is
  the project's own: declared in its own code (`builder.AddApplicationServices()`), or naming its own
  types — as type arguments (`AddScoped<IOrderRepository, OrderRepository>()`,
  `AddDbContext<OrderingContext>()`, `Configure<OrderingOptions>(…)`), in `typeof`, in a constructed
  object, or in a lambda (`AddMediatR(cfg => cfg.RegisterServicesFromAssemblyContaining<Program>())`).
  A call on what an earlier one returned configures that: `AddOptions<OrderingOptions>().Bind(…)`,
  `AddHttpClient<CatalogClient>().AddStandardResilienceHandler()` move whole.
  They go to `ConfigureServices(IHostApplicationBuilder builder)`, in their order, comments included.
- **Endpoint mappings** of the project's own endpoints: an `IEndpointRouteBuilder` extension on the
  application (or on `UseEndpoints`' route builder in a `Startup`) whose handler is written in the
  project (`app.MapGet("/orders", (IOrders o) => …)`), that names an own type
  (`MapGrpcService<OrderingService>()`, `MapHub<OrdersHub>(…)`), or that is an own extension
  (`app.MapOrdersApi()`). They go to `Configure(IApplicationBuilder app)`, inside
  `app.UseEndpoints(endpoints => …)`.
- **Locals** that only moved statements use, such as a connection string read into a variable,
  and a route group made from the application (`var api = app.MapGroup("/api")`) with the mappings
  made on it.
- **An `if` without `else`** around registrations that would move on their own, whose condition the
  module evaluates as the program did — it uses only what a moving statement may (below): the
  builder's environment or configuration (a `Startup`'s `Environment` and `Configuration`), locals that
  move with it, static members such as `OperatingSystem.IsWindows()`:
  `if (builder.Environment.IsDevelopment()) builder.Services.AddXxx<Own>();`. In the program and in a
  `Startup`'s `ConfigureServices` alike.
- **The project's own calls out of a chain** whose every call takes and returns the service
  collection: from `builder.Services.AddApplicationServices().AddInfrastructure(cfg).AddGrpcServices(cfg)`
  the module gets `builder.Services.AddGrpcServices(cfg);` and the program keeps the rest, in its order.
  So does `builder.Services.AddScoped<IOrderRepository, OrderRepository>().AddAuthentication()` when
  `AddAuthentication` returns the collection; when it returns its own builder, the chain stays whole.
- A **`Decorate`** of an own service, with the registration it decorates, and a **`PostConfigure`**
  of own options, which runs after every `Configure` wherever it is registered.

The builder is whatever `WebApplicationBuilder` the program makes — `WebApplication.CreateBuilder`,
or a service template's own factory around it — and locals that name a part of it
(`var configuration = builder.Configuration;`, `IConfiguration configuration = builder.Configuration;`,
`var services = builder.Services;`) are written as the module builder's own part; a local that only
moved code used goes. An assembly scan of the project's own assembly counts as its own code:
`Assembly.GetExecutingAssembly()`, `typeof(Program).Assembly` or a local holding one.

"The project's own code" is its source, plus every project it references — directly or through
another — that **no other program in the solution** references: the service's own Infrastructure or
Application project counts, a ServiceDefaults, BuildingBlocks or EventBus library shared with other
services does not. Programs that reference this one (its tests, an Aspire AppHost), test projects
and programs that are not web hosts are not counted against it: a worker that shares the service's
Application project is the same service's other half, and cannot become a module itself. With no other program loaded — `dotnet format` given the project alone —
only the project's source counts. The diagnostic cannot tell a shared project from an own one: it
counts the source first and, when nothing of the source's own moves, every project reference — so a
layered service whose `Program.cs` registers only its Application and Infrastructure projects' code is
reported too. The fix, with the solution in view, may then move fewer statements than the message
says, or none — it is offered on the diagnostic and plans the conversion only when it runs, and then
changes nothing. The diagnostic stays, with nothing to fix: the build cannot see that a project
reference is shared, or what its methods register. Once the conversion is done,
`dotnet_diagnostic.MOD0015.severity = none` in the project's `.editorconfig` silences it. In an IDE the
refactoring is offered on the same cheap answer the diagnostic gives.

An **own method** — `builder.AddApplicationServices()`, a project's `AddInfrastructure(…)` — moves
only if everything it registers is the project's alone. The fix reads its body, and the bodies of
the own methods it calls, the same way it reads the program: a call there that would stay if it were
written in the program — `AddAuthentication`, the shared event bus, `AddHealthChecks`, logging,
configuration sources — keeps the whole call in the program. A registration of someone else's
contract under an own implementation in it (`services.AddSingleton<TimeProvider, OrderingClock>()`)
holds the call to the same rule as in the program: it moves only when nothing before it stays. A
method whose source is not in the solution is taken at its word. The diagnostic reads only the
project's own source — in a build a project reference is metadata, and in an IDE it answers the same
way — so it takes a referenced project's methods at their word, and the fix may move less.

## What stays

Everything else stays in `Program.cs` or `Startup.cs`, unchanged:

- the framework's and the shared libraries' registrations — `AddControllers`, `AddAuthentication`,
  `AddServiceDefaults`, `AddOpenApi`, logging, OpenTelemetry, health checks, CORS, the shared event
  bus. Calls that shape the whole application (authentication, authorization, ASP.NET Core Identity,
  MVC, CORS, OpenAPI, ProblemDetails, exception handlers, feature management, the message bus —
  `AddMassTransit`, with its transport — and the job schedulers, Quartz and Hangfire…) stay even when their
  options name the project's types: a module of the monolith must not own them. So do a solution's
  service defaults by their usual names — `AddBasicServiceDefaults`, `AddDefaultAuthentication`,
  `AddDefaultOpenApi`, anything ending in `ServiceDefaults` or starting with `AddDefault`;
- a chain that starts with someone else's call, even if it goes on to name own types:
  `builder.Services.AddControllers().AddApplicationPart(…)`,
  `builder.AddEventBus("bus").AddSubscription<OrderStarted, OrderStartedHandler>()` — unless every call
  of it takes and returns the service collection, when only the own calls move (above);
- a registration of **someone else's contract** (`AddTransient<IProfileService, ProfileService>()`,
  `AddScoped<IClaimsTransformation, …>()`) after a statement that stays: the last registration wins,
  and in the module it would come before whatever the host registered first — Duende's
  `AddAspNetIdentity` registers an `IProfileService` of its own;
- middleware (`app.UseXxx`), migrations and seeding, `Run()` and anything after it, and any
  extension written against `WebApplication` itself;
- mappings that belong to the whole application whatever they name: `MapRazorComponents<App>()`
  (the Blazor shell, with its `/_blazor` endpoints), `MapFallback…` (a catch-all would answer for
  every module), `MapControllers`, `MapRazorPages` and the conventional controller routes (every
  controller or page at once), `MapOpenApi`, `MapSwagger`, `MapHealthChecks`, `MapStaticAssets`,
  `MapIdentityApi`, `MapDefaultEndpoints`;
- a statement that uses a local that stays, `args`, the application, the builder's `Logging`,
  `Host` or `WebHost`, or a `Startup`'s other members — the module would not have them;
- a statement nested in a loop or a block, an `if` with an `else`, or one whose condition or body uses
  what a moving statement could not (above) — only the program's (or `ConfigureServices`') own
  statements are read;
- a local function's call, and an own extension of the application itself (`app.UseApi()`), which may
  add middleware as well as endpoints;
- anything inside `#if`, or carrying a preprocessor directive;
- mappings in a `Startup.Configure` whose `UseEndpoints` is not its last statement (see below).

When endpoints move, the program has no `app.UseRouting()` and keeps no framework mapping written in
it (`app.MapControllers()`, `app.MapRazorComponents<App>()`, `app.MapReverseProxy()`…), the fix adds
`app.UseModuleRouting()` right after `builder.Build()` (and `using FusionModules;`). A mapping inside
a method does not count, own or shared: eShop's `MapDefaultEndpoints()` maps `/health` in Development
only, and in Production the program would have no endpoint, no routing, and a module whose
`UseEndpoints` throws at startup. A routing call too many costs nothing. `WebApplication` adds routing by itself
only while it has endpoints of its own, and the module's `UseEndpoints` needs it. A plain
`UseRouting()` there would not do: `WebApplication` also adds authentication, authorization and
antiforgery by itself when their services are registered, at the start of the pipeline — after
implicit routing, but before an explicit one, where no endpoint is chosen yet, and every endpoint
that requires authorization would answer 500. `UseModuleRouting()` adds routing and then those three,
as `WebApplication` would have. Like `WebApplication`, it decides about each of the three on its own:
what the program places itself — in `Program.cs` or inside an own `app.UseApi()` — is left out
(`app.UseModuleRouting(antiforgery: false)`), and a program that places all three gets a plain
`UseRouting()`. Only what it surely places: a `UseAuthentication()` under a condition, in the program
or in an own method, may not run, and then `WebApplication` would have added authentication itself —
so `UseModuleRouting` adds it, and when the condition holds it runs twice, which costs nothing.

## Order: what runs when

A module is a hosting startup, and that changes when its code runs.

- **Registrations run first.** A hosting startup's `ConfigureServices` runs while the builder is
  created — before every statement of `Program.cs`, and before a `Startup`'s `ConfigureServices`.
  Registrations that do not depend on order are unaffected. Those that do are left where they are:
  `Replace`, `RemoveAll` and other `Remove…` act on what was registered before them, and in the module
  there would be nothing yet; so do `PostConfigure…` and `Decorate…` of someone else's options or
  service. A plain `Add` of someone else's contract stays when anything before it stays (above). One
  of the project's own contract that the framework or a shared library also registers is the case the
  fix cannot see; `TryAdd` has the opposite problem. Read what moved with that in mind.
- **Configuration is read earlier.** A statement after one that adds configuration sources
  (`builder.Configuration.AddJsonFile(…)`, Key Vault, `builder.Host.ConfigureAppConfiguration`) stays if
  it reads the configuration when it runs; reading it inside a lambda, which runs later, is fine.
- **Hosted services start earlier.** A hosted service registered by a module is registered before
  the web server's own, so its `StartAsync` runs before the port opens (see
  [samples/05-startup](../../samples/05-startup/README.md)).
- **Endpoints come after the host's pipeline.** A module's `Configure` runs after the host has built
  its pipeline, so its `UseEndpoints` sits after all of the host's middleware. With
  `WebApplication` that is where the host's endpoints were too. In a `Startup`, mappings move only
  from a `UseEndpoints` that is the last statement of `Configure`: middleware written after it — a SPA
  fallback, a terminal `app.Run(…)` — would otherwise answer before the moved endpoints.

## Tidying

The fix removes the usings that only the moved code needed from `Program.cs`, and closes up the blank
lines the moved statements leave — unless the program had runs of blank lines already.

`dotnet format` also rewrites each converted project file: its workspace saves the project with the
added `<Compile Include="Module.cs" />` and, on the way, a byte-order mark, fewer blank lines, no final
line break. Nothing in it matters to the build. To keep the diff to the code, commit the
`PackageReference` first and restore the project files after the fix:

```bash
git checkout -- '*.csproj'
```

A solution that does not restore as a whole (an old project in it) can still be converted with
`--no-restore` after building what does.

Build or restore the solution right before running the fix. A project whose
`obj/*.assets.cache` is newer than its `project.assets.json` but predates the package reference —
seen after switching branches — loads without the package's analyzer, and `dotnet format` skips it
without a word; `dotnet restore --force` fixes that.

## After the fix

The project still builds and runs as one service. When it is time to join the monolith, the rest is
a project-file change: switch `Microsoft.NET.Sdk.Web` to `Microsoft.NET.Sdk`, drop `OutputType`,
delete `Program.cs` (moving to the host whatever of it the host needs once) and the `Compile` line
`dotnet format` added, and reference the project from the host.

## When it is reported

In a host — an `Exe` that references the package and is not a test project — that has no module of
its own yet and references no module, on the first statement that would move, and only if one would.
A project on .NET 7 or older gets the package's targets but neither its library nor its analyzers;
the build warns (`FUSIONMODULES001`) instead of staying silent. A worker built on
`Host.CreateApplicationBuilder` is not reported: a hosting startup runs only under the web host.
A host that composes modules is not a service on its way to becoming one; the refactoring is still
offered there, and adds to the host's module if it has one.
