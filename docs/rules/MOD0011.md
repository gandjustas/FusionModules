# MOD0011 — MVC never discovers the module's controllers or pages

**Severity:** Error · **Category:** FusionModules.Design · **Code fix:** yes

The module declares controllers, and MVC will never find them. Every route they map answers 404.
The application starts, the readiness probe passes, and nothing is logged.

MVC looks for controllers in its application parts. In an ordinary web application the SDK makes
every referenced MVC project a part of the host. This package turns that off for hosts
([MOD0007](MOD0007.md)), because a part the host adds is there in every topology, whether the
module was activated or not. So a module adds its own assembly, from its own `ConfigureServices`.

The second way to lose them comes from [MOD0001](MOD0001.md): a module's types are internal, and
MVC skips a controller that is not public unless the module calls `AllowInternalControllers()`.

The rule reports each controller MVC will not find, with the reason: no part at all, or a part and
an internal controller without `AllowInternalControllers()`.

## Violation

```csharp
sealed class Module : ModuleBase
{
    protected override void ConfigureServices(IHostApplicationBuilder builder) =>
        builder.Services.AddScoped<IOrders, Orders>();      // no AddControllers, no application part
}

[ApiController, Route("orders")]
internal sealed class OrdersController : ControllerBase  // MOD0011
{
    [HttpGet] public IActionResult Get() => Ok();
}
```

## Fix

```csharp
protected override void ConfigureServices(IHostApplicationBuilder builder)
{
    builder.Services.AddScoped<IOrders, Orders>();
    builder.Services.AddControllers()
        .AddApplicationPart(typeof(Module).Assembly)
        .AllowInternalControllers();
}
```

The code fix writes this. When the module already calls `AddControllers()` or
`AddControllersWithViews()` as a statement of its own, it appends to that call rather than adding a
second one, and `.AllowInternalControllers()` is added only when a controller is internal.

When the part is there and only `AllowInternalControllers()` is missing, the fix writes it right after
the module's `AddApplicationPart(...)`. A module that manages its parts with
`ConfigureApplicationPartManager` has no such call; the fix then writes it at the end of the statement
whose whole expression is the `IMvcBuilder` — `builder.Services.AddControllers().ConfigureApplicationPartManager(…)`.
When the builder is only ever passed along as an argument there is nowhere to write it, and the fix is
not offered rather than offered and doing nothing.

## What the rule looks at

- Controllers: top-level, non-generic, non-abstract classes deriving from `ControllerBase`, not
  marked `[NonController]`. A plain class that only ends in "Controller" is a controller to MVC as
  well, but it is rare in a module and is not reported.
- `AddApplicationPart` or `ConfigureApplicationPartManager` called anywhere in the module counts as
  the part being added. Which assembly the argument names is not checked.
- `AllowInternalControllers()` called anywhere in the module counts for every internal controller.

Razor pages and views are found through the same application part, so a module that adds it for its
controllers covers them too. A module that has pages or views and no controllers is reported on its
module class, found by the `RazorCompiledItem` attributes the Razor generator writes for each `.cshtml`;
the fix there registers `AddRazorPages()` (or `AddControllersWithViews()` for views) with the part. A
module whose only MVC types are view components is not reported.
