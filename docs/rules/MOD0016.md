# MOD0016 — Entity configuration and DbSet properties can move out of the DbContext

**Severity:** Info · **Category:** FusionModules.Usage · **Code fix:** yes

Not a defect. It marks a step of taking a `DbContext` apart: the configuration of each entity,
written in the context's `OnModelCreating`, becomes an `IEntityTypeConfiguration<T>` class in a
file of its own, and each `DbSet<T>` property of the context becomes an extension member of
`DbContext`. What is left is a context that names no entity type: `OnModelCreating` applies
classes, and `context.Orders` still reads the orders.

A model composed from modules is made of such classes. `ApplyModuleConfigurations`
([ef-core.md](../ef-core.md)) applies every `IEntityTypeConfiguration<T>` of the loaded modules, and
finds them by scanning each module's assembly, so a module keeps its configuration beside its
entities and takes both with it when it is loaded or left out. Configuration written in a context
belongs to that context: it cannot move with its entity. Once it is a class it can — to the module
that owns the entity, by moving a file. A `DbSet<Order>` property is the other thing that ties the
context to the entity: the host's shared context must not use a module's types
([MOD0004](MOD0004.md)), and a property is a use. An extension member in the entity's own project is
not the context's.

The diagnostic exists to carry the split as a code fix, so that it runs where refactorings do not:
`dotnet format`, a script, an agent. It is reported on `OnModelCreating` — on the context's name
when it has none — once per context, and only when something can move without the model changing.
Its message counts what moves and names what stays, each with its reason:

```text
'ShopContext': the configuration of 4 entity type(s) can move into IEntityTypeConfiguration<T>
classes and 5 DbSet propert(ies) can become extension members of DbContext; left in place: Order in
part uses the context's '_tenantId', property Audits implements IShopContext.Audits
```

## Run it

```bash
dotnet format analyzers Shop.slnx --diagnostics MOD0016 --severity info
```

Give it the **solution**: a property is read by projects that reference the context's, and with
only the context's project loaded those are not seen — before C# 14 their uses have to be rewritten,
and would not be. Without `--severity info` it skips the rule: a suggestion is below the default
`warn`. From Git Bash on Windows pass the path in Windows form, as for [MOD0015](MOD0015.md#run-it).

`dotnet format` writes a `<Compile Include="…Configuration.cs" />` line into the project file for
every file the fix adds (`…Extensions.cs` too), while the SDK includes the files by default already. The package's build
targets drop the duplicates ([msbuild.md](../msbuild.md#fusionmodulesdeduplicatemodulefile)), so the
build does not fail with NETSDK1022; the lines are redundant and can be deleted.

## What moves

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    base.OnModelCreating(modelBuilder);

    // Orders are looked up by number.
    modelBuilder.Entity<Order>(e =>
    {
        e.HasKey(o => o.Id);
        e.OwnsOne(o => o.ShipTo, address => address.Property(a => a.City).HasMaxLength(100));
    });

    modelBuilder.Entity<Customer>().ToTable("customers").HasKey(c => c.Id);
}
```

becomes

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    base.OnModelCreating(modelBuilder);

    modelBuilder.ApplyConfiguration(new OrderConfiguration());

    modelBuilder.ApplyConfiguration(new CustomerConfiguration());
}
```

```csharp
// OrderConfiguration.cs
internal sealed class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> e)
    {
        // Orders are looked up by number.
        e.HasKey(o => o.Id);
        e.OwnsOne(o => o.ShipTo, address => address.Property(a => a.City).HasMaxLength(100));
    }
}
```

A statement is the configuration of one entity, and moves, when it is

- `modelBuilder.Entity<T>(e => …)` with a lambda — its body becomes the body of `Configure`, under
  the lambda's own name for the builder;
- a chain on `modelBuilder.Entity<T>()` — `modelBuilder.Entity<T>().ToTable(…).HasKey(…)` becomes
  `builder.ToTable(…).HasKey(…)`;
- a private helper of the context that takes the entity's builder, handed over as
  `modelBuilder.Entity<T>(ConfigureOrder)` or `ConfigureOrder(modelBuilder.Entity<T>())` — its body
  moves and the helper goes;
- any of these inside a private helper of the context that `OnModelCreating` hands the model builder
  to (`ConfigureOrders(modelBuilder)`). The helper is read as if its statements stood where it is
  called, keeps what stays, and goes with its call when nothing is left in it.

Everything written inside such a statement moves with it: owned types (`OwnsOne`, `OwnsMany`),
relationships and many-to-many with `UsingEntity`, indexes, conversions, `HasData`, a query filter
that needs nothing of the context. Comments directly above a statement and inside it move too. Several
statements of one entity become one class, in the order they ran.

A **local variable** that only one entity's statements read — the seed list handed to `HasData` —
moves into `Configure` with them. A **static member or nested type of the context** that another
class can name (`internal const string Schema`) is written with the context's name:
`ShopContext.Schema`.

## DbSet properties

```csharp
internal sealed class ShopContext : DbContext
{
    public DbSet<Order> Orders { get; set; }
    public DbSet<Tag> Tag => Set<Tag>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>(e => e.HasKey(o => o.Id));
    }
}
```

becomes

```csharp
internal sealed class ShopContext : DbContext
{
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfiguration(new TagConfiguration());
        modelBuilder.ApplyConfiguration(new OrderConfiguration());
    }
}
```

```csharp
// ShopContextExtensions.cs, in the context's namespace
internal static class ShopContextExtensions
{
    extension(DbContext context)
    {
        public DbSet<Order> Orders => context.Set<Order>();
        public DbSet<Tag> Tag => context.Set<Tag>();
    }
}
```

A property did two things for the model, and a configuration class has to say both before the
property goes:

- **It put the entity in the model**, before `OnModelCreating` ran. A class puts it in where it is
  applied. An entity that had a property and no configuration gets a class of its own, applied as
  the method's first statement, in the order of the properties; a context without `OnModelCreating`
  gets one (with `base.OnModelCreating` after the classes, when its base is not `DbContext` itself).
- **It named the table**: `Orders` for `DbSet<Order> Orders`, where the entity's type alone would
  give `Order`. The entity's class gets `builder.ToTable("Orders")` — unless the name does not
  change (`DbSet<Tag> Tag`), the table is named already (`ToTable`, `ToView`, `[Table]`), or the
  entity derives from another entity of the context and shares its table.

The member is on `DbContext`, not on the context's own type, so that it reads the same from a
module's code that is handed a `DbContext`, and it is in the context's namespace, so that code which
names the context finds it.

- **C# 14**: an extension property. `context.Orders` stays as written, with the two exceptions the
  language makes. An expression tree may not read an extension property (CS9296), so a use inside
  one — a subquery `orders.Where(o => context.Customers.Any(…))`, a compiled query — becomes
  `context.Set<Customer>()`, which is what EF Core reads there anyway. And a member of the context
  itself says `this.Orders`.
- **Before C# 14** — in the context's project, or in any project of the solution that reads the
  property: an extension method, `Orders(this DbContext context)`, and every use gets its
  parentheses: `context.Orders()`. Inside expression trees it is `Set<T>()` here too: EF Core does
  not translate a call of somebody's method on a query's own parameter.

A file that uses the property without importing the context's namespace gets the `using`. The
class is `public` when the context is, `internal` otherwise.

## What stays, and why

In `OnModelCreating` stays what belongs to no single entity — `base.OnModelCreating`, a default
schema, sequences, `Owned<T>()`, conventions, a loop over `modelBuilder.Model.GetEntityTypes()`, a
library's `modelBuilder.AddOutboxStateEntity()` — and the configuration that could not be written in
another class, or not without the model changing. The message names the entity and the reason:

| Reason in the message | What it is |
|---|---|
| `uses the context's '…'`, `uses the context ('this')` | The statement reads an instance member of the context — a tenant filter `HasQueryFilter(o => o.TenantId == _tenantId)`, a condition on `Database.IsSqlite()` — or a private static one. A filter that names the context has to stay: EF Core evaluates it against the context of each query, and a value handed to a class's constructor would be read once, when the model is built, and cached with it. A class with constructor parameters would also not be found by any scan. Written as a statement of its own, the filter stays and the rest of the entity moves (`Order in part`); written inside the entity's lambda, it keeps the lambda. |
| `uses the local '…'`, `uses the parameter '…'` | It reads a local that another statement reads too — one seed object used by two entities' `HasData` — or a parameter of the helper it is in. |
| `uses the model builder` | The entity's lambda calls the model builder again. |
| `is configured inside a larger statement` | An `if`, a loop, a `using`: the condition is part of the model. |
| `is configured through a local variable` | `var order = modelBuilder.Entity<Order>(); order.HasKey(…);` |
| `is configured in a chain with other calls on the model builder` | `modelBuilder.Entity<A>(…).Entity<B>(…)` |
| `would run in another order against configuration that stays` | See [Order](#order) below. |
| `comes before its configuration class is applied` | The entity has a class already, and this statement runs before it. |
| `has '…', which this context does not apply in a way the fix can add to` | The project has a configuration class for the entity that this context does not apply with `ApplyConfiguration(new …())` or a scan — another context's, perhaps — or one whose `Configure` is not a block, or several. |
| `uses '…', which another class cannot name` | A private nested type, a type parameter of the context, a `file` type. |
| `is among preprocessor directives` | `#if` around or inside the statement. |

A DbSet property stays, with `property <Name>` in the message, when

| Reason in the message | What it is |
|---|---|
| `implements IShopContext.Orders` | An interface of the context asks for the property — `IApplicationDbContext` of a layered service. |
| `is static or can be overridden` | `virtual`, `abstract`, `override`: something mocks or replaces it. |
| `has attributes`, `is more than the context's set of the entity` | It is not an auto-property or `=> Set<T>()`. |
| `would come into the model after a statement that may read its entity types` | Its entity's class is applied after a loop over `modelBuilder.Model.GetEntityTypes()`, a library's extension of the model builder, the base call of a context whose base is not `DbContext` itself, or a helper the fix does not read. The property had put the entity in before any of them ran. Calls of EF Core's and the provider's own on the model builder (`HasDefaultSchema`, `HasPostgresExtension`) are not such statements. |
| `has configuration that stays in OnModelCreating and no class` | Nothing would say its table name. |
| `has '…', which this context does not apply…` | The entity's class is another context's, or cannot take the `ToTable`. |
| `is one of two sets of one entity` | `DbSet<Order> Orders` and `DbSet<Order> Archive`. |
| `names its table, and the provider is not a relational one` | There is no `ToTable` to say it with. |

and, which only the fix finds, reading the solution — the diagnostic stays for these — when the
property is **assigned**, named by **`nameof`**, a pattern or a documentation `cref`, or reached
through **`base`**; or the namespace already has an extension member of that name for another type.

So does a property whose name **another namespace** has given to an extension member of `DbContext`
already, where some code would find both. The member is on `DbContext`, not on the context, so two
contexts with a `Players` each — `auth.Repository.AuthDbContext` and
`shared.Data.CommonDbContext` — would leave two `Players` for one receiver, and a file that imports
both namespaces could not say which it means (CS9339; CS0121 for the methods). The first context the
fix reaches gets its member; the second keeps its property, which the context's own type finds
before any extension, if a read of either is in such a file. With no file that sees both, both go.

A context nested in another type is not read. Neither is `Entity(typeof(T))`, `Entity("name")` or
`SharedTypeEntity<T>(…)`: they stay, as statements nothing is moved across.

## How the classes are applied

The fix does not add a scan of its own: an `ApplyConfigurationsFromAssembly` written into a context
that had none would also apply whatever other configuration classes the assembly has.

- **Nothing scans the assembly** (the usual case before a migration): the first statement of each
  entity becomes `modelBuilder.ApplyConfiguration(new OrderConfiguration())`, where the entity's
  configuration stood. The entities are configured in the order they were.
- **The context composes its model from modules and its assembly is a module** — it calls
  `modelBuilder.ApplyModuleConfigurations(this)` and the project has an
  `[assembly: HostingStartup]` naming a `ModuleBase`: the statements are removed and nothing is added.
  `ApplyModuleConfigurations` finds the classes, as it does every module's. (At design time
  `KnownModules.Names` does not include a host that is itself a module; see
  [ef-core.md](../ef-core.md#for-dotnet-ef-and-tests).)
- **The context calls `ApplyConfigurationsFromAssembly`** on its own assembly
  (`typeof(X).Assembly`, `GetType().Assembly`, `Assembly.GetExecutingAssembly()`): the same — the
  scan finds the classes.
- **The context calls `ApplyModuleConfigurations(this)` but its assembly is not a module** — a host
  that is not one, a shared data project: the composition does not scan this assembly, so each class
  is applied with `ApplyConfiguration`, as in the first case.

The classes are `internal sealed` with the constructor a scan needs, so they are ready for the next
step: move `OrderConfiguration.cs` and `Order` to the module that owns them, and when the last one
has left, the context's `OnModelCreating` is `modelBuilder.ApplyModuleConfigurations(this)`.

That readiness has a consequence: **anything that scans the assembly finds the new classes.** In a
module that keeps a context of its own while the host's shared context composes its model from
modules, the shared context gets the entities the fix gave classes to — which is where a migration
is heading, and not what the module's private context meant. The rule cannot see another project's
context. Within one project it can: when another context of the project scans an assembly, the rule
is silent rather than add classes to that context's model.

### Order

EF Core applies configuration in the order it is written, and the later call wins where two set the
same thing. A loop over `modelBuilder.Model.GetEntityTypes()` sees the entities configured before
it and not those after. So nothing is moved across a statement that stays, and one entity's
statements are not moved across another entity's when either names the other's type — a relationship
configured from both ends.

With `ApplyConfiguration` this rarely matters: each class is applied where the entity's first
statement stood. It matters when an entity is configured in several places — the later statements
join the first only across statements they have nothing to do with — and with a scan, which applies
every class at the scan's place: a statement moves only when nothing between it and the scan depends
on the order.

## Where the files go

One file per entity, named for the class: `OrderConfiguration.cs`
(`OrderEntityConfiguration` when the namespace has an `OrderConfiguration` that is something else).

- A project that already has configuration classes has a place for them: the new files go to the
  folder and namespace most of them are in, and the context gets a `using` for it if it needs one.
- Otherwise beside the context's file, in the context's namespace.

The extension members go into one file per context, `ShopContextExtensions.cs` beside the context's
file, in the context's namespace; a second run adds to it.

Each file gets the usings of the context's file that its code needs and no others, the namespace
style of the context's file (file-scoped or a block), its indentation, its line endings and its
encoding, byte order mark included. The context loses the usings only the moved code needed.

**A class that configures the entity already** takes the statements: when the context applies it
(`ApplyConfiguration(new OrderConfiguration())`, or a scan) before them, they are added at the end
of its `Configure`, under its name for the builder.

## Checking the result

The inventory records every context's model, and comparing two of them compares the models
([inventory.md](../inventory.md#comparing-two-inventories)):

```bash
dotnet modules inventory Shop.slnx -o before.json
dotnet format analyzers src/Shop.Data/Shop.Data.csproj --diagnostics MOD0016 --severity info
dotnet modules inventory Shop.slnx -o after.json --compare before.json
```

Every host "the same" means every entity type has the table, properties, keys, indexes,
relationships, query filters and seed data it had — the table name a removed property gave included.

## Running it again

Changes nothing: what the fix left in place stays for the reasons it stayed, and a context with
nothing to move is not reported. A property the fix left for how it is used — assigned, named by
`nameof` — is still reported: the analyzer reads the context and not the solution's uses of it.

## What the fix does not see

- **Razor.** A `.cshtml` or `.razor` file that reads `context.Orders` is not C# source to the fix.
  With C# 14 it keeps compiling as long as it imports the context's namespace; before C# 14 it
  needs its parentheses by hand.
- **Code outside the solution.** Removing a public property of a public context is a breaking
  change for whoever compiled against it.
- **Reflection** over the context's properties — a library that lists the `DbSet` properties of a
  context finds none.

## Cost

The analyzer reads only methods named `OnModelCreating` that override one, and nothing at all in a
project that does not reference EF Core. See [performance.md](../performance.md).
