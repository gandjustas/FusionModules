# MOD0005 — A module must be named by an assembly-level HostingStartup attribute

**Severity:** Error · **Category:** FusionModules.Design

Without the attribute the module fails silently, which is the worst way for anything to fail.

The assembly is listed in `HOSTINGSTARTUPASSEMBLIES`. ASP.NET Core loads it, looks for a
`HostingStartupAttribute`, finds none, and moves on. The application starts. The readiness probe
passes. The module's services and endpoints simply do not exist, and nothing anywhere says so —
the first sign is a 404 in an environment where the module was supposed to be live.

## Violation

```csharp
sealed class OrdersModule : ModuleBase { }   // MOD0005: nothing names it
```

## Fix

```csharp
[assembly: HostingStartup(typeof(OrdersModule))]

sealed class OrdersModule : ModuleBase { }
```

The attribute allows multiple, so one assembly may carry several modules — each needs its own
attribute.

An `abstract` class deriving from `ModuleBase` is not reported: a shared base for your own
modules is not itself a module.

## At runtime

`ModuleBase` makes the same check from the other side: if a name in `HOSTINGSTARTUPASSEMBLIES`
resolves to an assembly with no `HostingStartupAttribute`, startup fails rather than serving
404s. That check runs from whichever modules did load, so it cannot help when *every* name is
wrong — which is why the rule exists at build time as well.
