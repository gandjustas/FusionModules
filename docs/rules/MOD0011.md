# MOD0011 — The host does not validate its modules

**Severity:** Warning · **Category:** FusionModules.Usage · **Code fix:** yes

ASP.NET Core loads the assemblies named in `HOSTINGSTARTUPASSEMBLIES` while it creates the builder.
For a name it cannot load it logs a critical message and carries on. The application starts,
passes its readiness probe and serves 404s for everything the missing module would have mapped.

`ValidateModules()` turns that into a startup failure. The package generates it into the host,
from the host's project references, next to [`KnownModules`](../msbuild.md#fusionmodulesknownmodules).
It compares the variable with that list:

- every name has to be loaded in the process — a typo, or an assembly not deployed next to the
  host, fails;
- a name that is one of the host's modules has to have run its startup — one excluded by
  `HOSTINGSTARTUPEXCLUDEASSEMBLIES`, say, fails.

A name that is not one of the host's modules, such as a third-party hosting startup, only has to
load.

This rule reports a host that loads modules and never passes its builder to `ValidateModules()`.

## Violation

```csharp
var builder = WebApplication.CreateBuilder(args);   // MOD0011
var app = builder.Build();
```

```csharp
Host.CreateDefaultBuilder(args)
    .ConfigureWebHostDefaults(web => web.Configure(app => app.UseRouting()))   // MOD0011
    .Build()
    .Run();
```

## Fix

`WebApplication`: call it where the builder is created. The hosting startups have run by then, so
this is the earliest point the check can say anything:

```csharp
var builder = WebApplication.CreateBuilder(args).ValidateModules();
```

Generic host: call it anywhere in the chain. The overload for `IHostBuilder` registers the check to
run when the host is built, which is when that host runs the hosting startups:

```csharp
Host.CreateDefaultBuilder(args)
    .ConfigureWebHostDefaults(web => web.Configure(app => app.UseRouting())).ValidateModules()
    .Build()
    .Run();
```

The code fix writes either, and adds `using Microsoft.Extensions.Hosting;` when implicit usings are
off.

## When it is reported

- Only in a project that has `ValidateModules()`: a host, with the module list not switched off
  by `FusionModulesKnownModules=false`. A test project creates hosts of its own and is left alone.
- Only in a host that references at least one module. Adding the package to a web project that
  has no module yet is not a mistake, and its first build stays clean; the warning comes with the
  first module reference.
- For the two shapes that load modules, because only ASP.NET Core's `GenericWebHostBuilder` runs
  hosting startups: `WebApplication.CreateBuilder`, and a generic host (`IHostBuilder`) with
  `ConfigureWebHostDefaults` or `ConfigureWebHost` on it. `WebApplication.CreateSlimBuilder`,
  `CreateEmptyBuilder` and `Host.CreateApplicationBuilder` run none, so no module loads into a host
  built with them and there is nothing to validate.
- A generic host reads `HOSTINGSTARTUPASSEMBLIES` from `ASPNETCORE_` environment variables and
  `UseSetting` only: command-line arguments reach its configuration after the startups have run.
- A builder counts as validated when a `ValidateModules()` call in the same method receives it:
  directly, further along a fluent chain, or through the local it was stored in. A builder the
  method returns — the classic `CreateHostBuilder(args)` — is its caller's to validate and is not
  reported. A builder handed to a helper method that validates it is not followed; suppress the
  warning there and say where the check happens:

```csharp
#pragma warning disable MOD0011 // validated in HostSetup.Configure
var builder = WebApplication.CreateBuilder(args);
#pragma warning restore MOD0011
HostSetup.Configure(builder);
```
