# MOD0017 — Two modules map one table or one entity

**Severity:** Error · **Category:** FusionModules.Usage

A new module needs another module's data. Referencing that module would change the topology, so it
does this instead:

```csharp
// Billing module
class Order { public int Id { get; set; } public decimal Amount { get; set; } }   // its own copy

class OrderConfiguration : IEntityTypeConfiguration<Order>
{
    public void Configure(EntityTypeBuilder<Order> entity) => entity.ToTable("Orders", "Sales");   // the Orders module's table
}
```

There is no reference between the assemblies, the compiler is satisfied, and everything works until
the Orders module changes its schema. The same leak comes through a shared assembly: two modules
configure one entity class, each with a `ToTable` of its own, and EF Core silently keeps whichever
was applied last.

A table has one owning module, the one that names it; so does an entity. This rule reports a table
or an entity that two of the host's modules name.

## How it is found

The host's build is the only one that sees every module, but it sees them as metadata, and a call to
`ToTable` lives in a method body that metadata does not keep. So the work is split, as for
[MOD0014](MOD0014.md): the package's generator runs in each module's build and records the tables
the module maps as internal assembly attributes, and the host's analyzer reads those attributes back
from every module the host references. The attributes are internal, so they add nothing to the
module's surface, and they survive reference assemblies.

Recorded, when the names are constants (a literal, a `const`, `nameof`):

- `ToTable` on an entity's builder — in an `IEntityTypeConfiguration<T>`, on `modelBuilder.Entity<T>()`
  or in `modelBuilder.Entity<T>(b => …)` — with every overload that names a table:
  `ToTable(name)`, `ToTable(name, schema)`, `ToTable(name, buildAction)`,
  `ToTable(name, schema, buildAction)`. It records the table and the entity.
- `[Table("Orders", Schema = "Sales")]` on an entity class the module declares. It is the same
  constant written as an attribute, and it records the table and the class.
- `ToTable` on an owned type's builder, `SplitToTable`, and `ToTable` on a builder of no particular
  type (`modelBuilder.Entity(typeof(T))`). They record the table only: the entity's own `ToTable`
  is the one that says who owns the entity.

Not recorded:

- a name that is not a constant — read from configuration, built at run time. The generator does not
  guess. Neither does it record a constant table whose schema is not a constant;
- `ToTable(null)` and `ToTable(table => …)` without a name;
- `ToView`, `ToSqlQuery`, `ToFunction`. A view or a query is how a module reads data it does not
  own, which is one of the fixes below, not the leak. Two modules mapping one view read the same
  data and change nothing; whoever creates the view in a migration owns it, and EF Core does not
  create views;
- a configuration of another module's entity that names no table: a relationship, an index, a
  property. A composing module, like `BillingModule` in [samples/03](../../samples/03-modular-data),
  configures the Orders module's `Order` and does not own it;
- a generic helper's type parameter: `EntityTypeBuilder<T>` in a helper maps a different entity at
  every call.

## How keys are compared

There are two kinds of key, and a mapping can collide on either.

**An entity** is compared as a type together with its assembly. Two modules that each declare an
internal `Shop.Note` have two entities, and the rule leaves them alone; one class in a shared
assembly that two modules map with `ToTable` is reported, as `'Shop.Order'`, whether the two tables
are one or two.

**A table** is compared as `schema.name`, without regard to case. SQL Server and SQLite compare
names so by default; on PostgreSQL, where quoted names are case-sensitive, `Orders` and `orders` are
two tables, but two modules naming tables that differ only in case is a trap worth a look anyway.

A table without a schema is not the table of a named schema: `ToTable("Orders")` and
`ToTable("Orders", "Sales")` are two keys. Where an unqualified table ends up depends on the
provider's default schema (`dbo`, `public`, none) and on `HasDefaultSchema`, which the build does not
know. `HasDefaultSchema` is not read either: it is called on the model builder of the context that
composes the model, rarely in a module, and a constant one would still be the host's, not the
module's.

Several entities of **one** module on one table — table splitting, an owned type kept in its owner's
table, a hierarchy mapped to one table — are not a collision: the table has one owner.

## Violation

```csharp
// Orders.Entities
entity.ToTable("Orders", "Sales");

// Billing, with its own Order class
entity.ToTable("Orders", "Sales");

// the host references both:
// error MOD0017: 'Sales.Orders' is mapped by modules Billing, Orders.Entities; a table and an entity have one owning module, the one that names the table
```

If Billing configures the Orders module's own `Order` under a table of its own instead, the error is
about `'Orders.Order'`. Modules are named in alphabetical order.

## Fix

The rule does not decide whose table it is; there is no code fix. Pick an owner, and then:

- **Read through the owner's contract.** The module that needed the data asks the owning module for
  it — a service in a contracts assembly, an endpoint, an event it keeps a copy from. Its own copy of
  the entity, and its `ToTable`, go away.
- **Move the entity to the owner, and reference it.** One class, in the owning module, configured
  there with `ToTable`. The other module references the owner's assembly and configures what it adds —
  a relationship, as `BillingModule` does — without naming the table.
- **Read through a view or a query.** `ToView("OrderSummaries", "Sales")` or `ToSqlQuery(…)` maps
  an entity for reading without owning a table. The view is the owner's to create and to keep
  compatible.

## Modules that are never loaded together

The check covers every module the host references at once, so it is stricter than any one topology.
Two modules may be alternatives — a real payments module and a fake one, each mapping the payments
table — and no deployment loads both. In that case, list the table or the entity, as the message
names it, in `.editorconfig`:

```ini
[*.cs]
fusion_modules_allowed_table_collisions = Sales.Payments, Shop.Payment
```

A table is matched with its schema and without regard to case; an entity by any of the names
[MOD0014's list](MOD0014.md#modules-that-are-never-loaded-together) accepts for a type, short or
full. A project file can set it as an MSBuild property of the same name:

```xml
<PropertyGroup>
  <fusion_modules_allowed_table_collisions>Sales.Payments</fusion_modules_allowed_table_collisions>
</PropertyGroup>
```

When one entity is mapped by two modules, the message names the entity, and the entity is what to
list; listing its table does not cover it.

## What it cannot see

Only constants written in the modules' own code. A table named by convention — from a `DbSet`
property or the class name — a name read from configuration, and a `ToTable` inside a shared
library's helper are invisible here. A module whose context sets `HasDefaultSchema` puts its
unqualified tables in a schema the rule does not know.

The rule runs in the host's build only — not in a test project — and only for the modules the host
references.
