# MOD0001 — A module must not expose public types

**Severity:** Error · **Category:** FusionModules.Design

A module's types are an implementation detail. If nothing outside the module can name them,
nothing outside the module can depend on them, and the module stays replaceable — which is the
only reason to have modules at all.

This also makes [MOD0003](MOD0003.md) enforceable: the host cannot accidentally use what it
cannot see.

## Violation

```csharp
[assembly: HostingStartup(typeof(Module))]

sealed class Module : ModuleBase { }

public class Order { }   // MOD0001
```

## Fix

Make the type `internal`. The code fix does this, and Fix All does it for a whole project — which
is how a service converted into a module is usually cleaned up in one pass.

```csharp
internal class Order { }
```

If another module genuinely needs the type, it is not an implementation detail: move it to a
plain contracts library — an ordinary `Microsoft.NET.Sdk` project with no `[HostingStartup]` —
which both modules reference. That library is not a module, so this rule does not apply to it.

## Exempt by default

Types the framework may need to be public, and which are therefore not reported:

- controllers (`ControllerBase`)
- page models (`PageModel`)
- view components
- tag helpers (`ITagHelper`)
- SignalR hubs (`Hub`), and the client interface of a `Hub<TClient>`
- entity types configured by an `IEntityTypeConfiguration<T>` **in the same assembly**

"May need to be" rather than "cannot be internal": for three of those the requirement can be lifted
or was never there, and the next section says which.

The last one is worth dwelling on: the configuration is the evidence. A public class with no
configuration is reported, because from the outside it is indistinguishable from a leak. The hub
client is the same idea: the `Hub<TClient>` in this assembly is what proves the interface is one.

## The cascade, and what to do about it

Exempting a controller is true and not sufficient, and the gap is worth knowing before you start
converting a service that has any.

A public class cannot have a public constructor taking an internal service, nor a public action
returning an internal DTO. So a public controller drags its dependencies and its models public
with it, and then whatever those name, until most of the module is public and the rule has bought
you nothing.

Turn it round. Keep the controller internal and let discovery see it:

```csharp
services.AddControllers()
    .AddApplicationPart(typeof(Module).Assembly)
    .AllowInternalControllers();
```

The class becomes `internal`, **the constructor stays public** — MVC's activator reads
`GetConstructors()`, which is public-only — and from there the constructor may take internal
parameters and the actions may return internal types, because C# bounds a member's effective
accessibility by its containing type. One call configures discovery for the whole application.

The exemption stays for anyone who has not made that call, and it is still correct for them.

### View components: the same answer, reached differently

```csharp
services.AddControllersWithViews()
    .AddApplicationPart(typeof(Module).Assembly)
    .AllowInternalViewComponents();
```

MVC's test for a view component is a static method rather than a virtual one, so there is nothing
to override and nothing to replace; this adds a second feature provider that contributes the
internal ones. As with a controller, `Invoke`/`InvokeAsync` stays public and may take and return
internal types.

Invoking it from a view works both ways — `@await Component.InvokeAsync("Tiles")` and
`@(await Component.InvokeAsync<TilesViewComponent>())`. Both resolve at run time against the
descriptor collection, and the generic form compiles because the class Razor generates for a view
is itself `internal` and sits in the same assembly as the component.

One form does not work: **`<vc:tiles />`**. That one is bound by the Razor compiler, which requires
a public type — and reports nothing when there is none. The element is copied into the rendered
page as literal HTML: no build error, no warning, no exception, just markup where the component
should have been. If you want the element syntax, keep the component public.

### Razor Pages: nothing to do

An internal `PageModel` already works, and always did. Razor Pages does not scan for types: it
reads the `[RazorCompiledItem]` attributes the Razor compiler emits, and the page class generated
for a `.cshtml` is itself `internal sealed`, so an internal model is exactly what it is built for.

What must stay public is the constructor — `ActivatorUtilities` only considers public ones — and
the handler methods, which are found with `GetMethods()`. The `.cshtml` and its model must be in
the same assembly, which for a module they are.

The exemption above remains for the cases that do need a public page model; needing one is rarer
than its presence on the list suggests.

### Tag helpers: keep them public

There is no way round this one, and it fails in the worst way available.

`@addTagHelper` is resolved by the Razor compiler against Roslyn symbols, and its test requires
`public` — for types in the current assembly as much as for referenced ones. An internal tag helper
produces no descriptor, so `<my-tag>` matches nothing and is emitted into the page as literal HTML.
No build error, no warning, no runtime exception: the element is just gone from the rendered output
and present in the source. The runtime's own feature provider does not check visibility, which
makes this look survivable right up until you render the page.

So a tag helper is a genuine public type in a module. If its constructor or properties would drag
internals out with it, take the data in as primitives, or move the tag helper to a contracts
library where public is the point.

## When the rule is wrong

Real solutions have public types the analyzer cannot infer a reason for: a DTO bound by a
source-generated `JsonSerializerContext` in another assembly, a gRPC service base, a message
contract a broker library discovers by reflection. Allow them by name:

```ini
# .editorconfig
[*.cs]
fusion_modules_allowed_public_types = OrderDto, PaymentEnvelope
```

Or suppress one occurrence:

```csharp
#pragma warning disable MOD0001 // Bound by OrderSerializerContext in Contracts.
public class OrderDto { }
#pragma warning restore MOD0001
```

Prefer the `.editorconfig` list when the exception is structural and the pragma when it is local.
Either way, write down why — the next reader cannot tell a considered exception from an
abandoned one.

A hub's client interface used to belong on that list and no longer does. It is exempt here and
[MOD0009](MOD0009.md) asks the question that actually matters about it: whether SignalR's generated
proxy can reach it. An entry here would have recorded no decision, because the runtime leaves none
to make.
