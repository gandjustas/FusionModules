# EF Core: a model composed from the loaded modules

`FusionModules.EntityFrameworkCore` is a separate package, so that `FusionModules` itself does not
depend on EF Core. It does for a shared context what every modular application with one ends up
writing by hand: compose the model from the entity configurations of the modules the host loaded,
and cache one model per set of modules.

```bash
dotnet add package FusionModules.EntityFrameworkCore
```

It targets `net8.0` and `net10.0`, like `FusionModules`, and depends on `FusionModules` of the same
version and on `Microsoft.EntityFrameworkCore` 8.0.10 or 10.0.0 and later respectively. Those are
floors, not what it asks you to run: the package raises nothing in an application that references a
later EF Core, so the application's provider and EF Core stay at one version. (8.0.10 rather than
8.0.0: earlier EF Core 8 releases depend on a `Microsoft.Extensions.Caching.Memory` with a security
advisory.)

## In the host

```csharp
using FusionModules.EntityFrameworkCore;   // UseModules, ApplyModuleConfigurations
using Microsoft.EntityFrameworkCore;

builder.Services.AddDbContext<AppContext>(options => options
    .UseNpgsql(builder.Configuration.GetConnectionString("Postgres"))
    .UseModules(builder.Configuration));

sealed class AppContext(DbContextOptions<AppContext> options) : DbContext(options)
{
    protected override void OnModelCreating(ModelBuilder modelBuilder) =>
        modelBuilder.ApplyModuleConfigurations(this);
}
```

With Aspire's `AddNpgsqlDbContext<AppContext>`, call `UseModules` in `configureDbContextOptions`.

The modules keep their entities and `IEntityTypeConfiguration<T>` classes in their own assemblies
and reach them with `Set<T>()` on a `DbContext` the host registers
(`services.AddTransient<DbContext>(sp => sp.GetRequiredService<AppContext>())`).

## For `dotnet ef` and tests

Outside a host there is no registry of activated modules; name them instead. `KnownModules.Names`
is every module the project references, generated by the package:

```csharp
using FusionModules;                       // KnownModules, generated into the project
using FusionModules.EntityFrameworkCore;   // UseModules
using Microsoft.EntityFrameworkCore;

var options = new DbContextOptionsBuilder<AppContext>()
    .UseNpgsql(connectionString)
    .UseModules(KnownModules.Names)
    .Options;
```

`KnownModules.Names` lists the modules a project *references*, so a host that is itself a module —
one with its own `[assembly: HostingStartup]` and entity configurations — is not among them. At
runtime ASP.NET Core activates such a host first and `UseModules(builder.Configuration)` includes it;
at design time add its name yourself (`UseModules([typeof(Program).Assembly.GetName().Name!, ..KnownModules.Names])`),
or the migration is missing its tables. Named, it is ordered with the modules — after the ones it
references, otherwise by name — rather than first.

Migrations are generated for the union of every module and applied whole, whatever a topology
loads.

## What it does

- **`UseModules`** reads the modules from `ModuleBase.GetLoadedModules` — or from the names, through
  the same registry (`ModuleBase.CreateModuleRegistry`) — and keeps them in the context's options.
  One options extension is kept per module set, so building the options for every scope costs
  next to nothing.
- **It replaces EF Core's `IModelCacheKeyFactory`** with one whose key is the context type, the
  module set and the design-time flag. EF Core caches a model per context type, so without it a
  second host in the same process, as in any integration-test assembly, silently gets the first
  one's tables. A context that replaces `IModelCacheKeyFactory` itself — for a schema per tenant,
  say — replaces this one too, whichever `ReplaceService` comes last; its key then has to include
  `context.GetModuleSetKey()`, or the two are no longer composed:

  ```csharp
  sealed class TenantModelCacheKeyFactory : IModelCacheKeyFactory
  {
      public object Create(DbContext context, bool designTime) =>
          (context.GetType(), ((AppContext)context).Schema, context.GetModuleSetKey(), designTime);
  }
  ```
- **`ApplyModuleConfigurations`** applies every `IEntityTypeConfiguration<T>` of those modules, in
  `GetLoadedModules` order: **the host's own module first**, when the host is one, then each module
  after the modules it references, and modules that do not depend on each other by name. A module
  that adds to another's configuration — a relationship between two entity modules' tables — uses
  their types, references them, and is applied after them wherever `HOSTINGSTARTUPASSEMBLIES` lists
  it. The host's own module comes first because ASP.NET Core activates it first: where the host and
  a module configure the same thing on one entity, the module's configuration, applied later, wins.
  An addition to a module's entities belongs in a module that references it.
- Modules without configurations are skipped rather than scanned, and a module whose optional
  dependency is not deployed still has its configurations found: the types that load are scanned.
- Called on a context whose options never got `UseModules`, `ApplyModuleConfigurations` throws an
  `InvalidOperationException` that says so.

The package registers nothing in the application's container: the options extension and the cache
key factory live in EF Core's internal service provider. The startup check for two modules
registering one service, and MOD0014 in the host's build, have nothing of it to see — and EF Core's
`DbContextOptions`, which `AddDbContext` registers, is shared by design in both.

## What it logs

Once per model EF Core builds — a model is cached per set of modules and per design-time flag, so
a host that also builds the design-time model, migrating say, may write it twice — a line in the category
`FusionModules.EntityFrameworkCore`, at `Information`, beside the host's `Topology:` line:

```text
Model of AppContext: configurations from: Customers.Entities (Customer), Orders.Entities (Order),
BillingModule (Order); without configurations: CustomersModule; configured by several modules:
Order (Orders.Entities, then BillingModule)
```

Written like the host's [`Topology:` line](runtime.md#the-startup-report): every part `label: value`,
separated by `;`, and a part with nothing to say left out rather than written as `none`:

| Part | Field | What it says |
|---|---|---|
| `configurations from` | `Modules` | The modules with configurations, in the order they were applied, each with its entities. |
| `without configurations` | `Without` | The modules that had none. |
| `configured by several modules` | `Shared` | Every entity more than one module configures, with its modules in the order their configurations were applied. |

The context's type name is the `Context` field. Every field is on every entry, empty or not, so a log
store finds the same fields for every model; a context over no modules at all writes
`Model of AppContext: no modules`. When a table is missing in one topology, this is the line that
says which module it would have come from.
