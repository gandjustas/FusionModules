# MOD0014 — Two modules register one service with different implementations

**Severity:** Warning · **Category:** FusionModules.Usage

Before the merge, each service had a container of its own, and an interface could mean one thing
in each. The modules now share one container. For a service resolved as one instance, the last
registration wins, or the first one with `TryAdd`. Either way one module gets an implementation it
did not register, and nothing says so. In eShop this was `IIntegrationEventLogService`: the
Catalog and Ordering outboxes each registered their own, and one module wrote its events through
the other's `DbContext`.

At startup `ModuleBase` checks the same thing (see
[runtime.md](../runtime.md#two-modules-registering-one-service)). This rule asks the question in the
host's build, before anything runs.

## How it is found

The host's build sees modules only as metadata, and metadata keeps no record of a call to
`AddSingleton`. So the package's generator runs in each module's build and records the services
the module's code registers as internal assembly attributes. The host's analyzer reads those
attributes back from every module the host references. The attributes are internal, so they add
nothing to the module's surface, and they survive reference assemblies.

Recorded: `Add{Singleton|Scoped|Transient}` and `TryAdd{Singleton|Scoped|Transient}`, generic or
with `typeof`, and a typed `HttpClient` — `AddHttpClient<TClient, TImplementation>()`, the usual way a
remote implementation of a contract is registered. The implementation is the type argument, the
`typeof`, the instance's type, or a factory. A factory counts as an implementation of its own, as it
does at runtime: two modules' factories differ even when they build the same type.

Not recorded:

- keyed registrations, because two keys are two services;
- `TryAddEnumerable`, which declares a sequence;
- the framework's own contracts (`System.*`, `Microsoft.Extensions.*`, `Microsoft.AspNetCore.*`
  and the rest of the runtime check's list), which are extension points registered as sequences,
  and EF Core's non-generic `DbContextOptions`;
- contracts marked with an attribute named `MultipleImplementationsAttribute`;
- a type parameter of a generic helper.

Types are compared together with their assemblies. Two modules that each declare an internal
`Shop.IChecker` register two different services, and the rule leaves them alone.

The rule runs in the host's build only — not in a test project — and only for the modules the host
references.

## Violation

```csharp
// Orders module
services.AddSingleton<IChecker, OrdersChecker>();

// Billing module
services.AddSingleton<IChecker, BillingChecker>();

// the host references both: MOD0014 'Shop.IChecker' (Billing: Shop.BillingChecker; Orders: Shop.OrdersChecker)
```

## Fix

- **A keyed service**, with each module resolving its own key: `AddKeyedSingleton<IChecker, OrdersChecker>("orders")`
  and `[FromKeyedServices("orders")]`.
- **A service type of each module's own**, e.g. `IOrdersChecker`. Often the interface was only
  shared because the code was copied.
- **`[MultipleImplementations]` on the contract**, when consumers take `IEnumerable<IChecker>` and
  every implementation is meant to be there. Declare the attribute wherever the contract is; it is
  matched by name.

`TryAdd` is not a fix. It turns "last wins" into "first wins", and one module still gets the wrong
implementation.

## Modules that are never loaded together

The host references every module it can load. The build cannot tell which of them a deployment
loads together. Two modules may be alternatives, one per topology: a real payment gateway and a
fake one, for example. In that case, list the service in `.editorconfig`:

```ini
[*.cs]
fusion_modules_allowed_service_collisions = IPaymentGateway, Shop.IClock
```

Names may be short or full, with the same spellings the runtime's
`FusionModules:AllowedServiceCollisions` accepts (see [runtime.md](../runtime.md#naming-a-type)). A
project file can set it as an MSBuild property of the same name:

```xml
<PropertyGroup>
  <fusion_modules_allowed_service_collisions>IPaymentGateway</fusion_modules_allowed_service_collisions>
</PropertyGroup>
```

If such modules are ever loaded together after all, the startup check still stops them. The
generated `ValidateModules()` hands the list to it as `FusionModules:AlternativeServices`, so its
message names the modules as alternatives and asks to load only one (see
[runtime.md](../runtime.md#alternatives-the-hosts-build-already-knows)).

## Which list, when

Two checks ask the same question at different times, and each has its own way of being told "this is
intended". Which one a case needs depends on what the build can know:

| Case | This rule (build) | Startup check |
|---|---|---|
| A contract you own, read as `IEnumerable<T>` | `[MultipleImplementations]` on it | the same attribute — nothing else |
| Alternatives no topology loads together | `fusion_modules_allowed_service_collisions` | nothing: they never meet; if they do, it stops them, which is right |
| A contract you do not own, read as a sequence by modules that run together (MediatR's `INotificationHandler<T>`) | `fusion_modules_allowed_service_collisions` | `FusionModules:AllowedServiceCollisions` in each host's configuration |

The startup check cannot read `.editorconfig`, and the build cannot read a deployment's configuration,
so the last case is written twice. It is also the only one that needs the runtime list at all.

## What it cannot see

Only registrations written in the module's own code are seen. A registration made inside a
library's extension method, such as `AddIntegrationEventLog()` in a shared package, is invisible
here. The startup check sees those. The two checks complement each other: the startup check misses
a `TryAdd` that never took effect, and this rule catches it.

A registration on a code path that never runs is still recorded. That is part of why this is a
warning.
